## Retroactive controls — read before changing these

A retroactive control re-prices existing save data. It is not a setting that takes effect from now on; it rewrites what has already happened, and the result persists into the save, so putting the control back does not put the save back.

| Subsystem | Field | What it re-prices |
|---|---|---|
| Progression | **`enabled`** | Recompute Team Power Level from the 'override' section instead of the game's table. 3.0 moved this switch out of the cfg key [Progression] Enabled and into this section; it is the whole enable chain for this subsystem. ALWAYS RETROACTIVE: turning it on re-prices every past mission at load, and the substituted total persists into the save, so turning it back off leaves a modded figure behind. RetroactiveTable was removed in 2.12.0 — it was this subsystem's only mode, so it had nothing left to switch, and the other three levers (GainScalar, GainOverride and a 'remap' list, all of which worked by rewriting a row's join keys so the award had to snap to one of the 63 shipped cells) went in 2.11.0 (Progression.cs:49-60). HOW TO TELL IT IS WORKING: before substituting anything the plugin sums the GAME'S values over the same rows and compares them with what the game just returned, and logs 'Progression: reconciled <total> over <n> row(s).' when they agree. If that line does not appear, the plugin could not reproduce the game's own total and has left Team PL exactly as the game computed it — on purpose, not because the subsystem is off (Progression.cs:291-322). To watch the award itself, trace RPG.Database.GameDb.SumGameMissionScore; that setting belongs to the separate CKF Data Dump plugin's [Diagnostics] section, not to any key this schema declares (Plugin.cs:57-58). The victory screen is not evidence either way — it reads a different path at a different time. |
| Progression | **`override`** | Per-cell replacement for the award. A cell absent here keeps its 'table' value, and a cell present here replaces it outright - the value is used verbatim, with no snapping to a shipped cell and no clamp of any kind in the code (Progression.cs:150-152, 340-342). A cell with no 'table' value works too: it simply contributes its own figure to the sum, and gen_teampl_labels.py emits its label rule marked '(no stock cell)'. THE RANGES BELOW ARE GUARD RAILS FOR THE EDITOR, NOT ENGINE LIMITS. ActionClass runs 0-3 because that is what the save files rows under; the shipped table has no class-0 band, so a class-0 override has no stock value behind it and re-prices every LEGWORK row from zero. PowerLevelFraction is allowed to go negative because the game's own table does. A worked example: an override cell of ActionClass 2, MissionPowerLevel 7, PowerLevelFraction 0.015 makes Treaty contracts at PL 7 pay a solo hack's rate, 0.03 down to 0.015, and setting the same cell to 0 stops that class and level advancing the team at all. |

## Difficulty

**Custom Difficulty Slider Range** &nbsp;·&nbsp; `ckf.hardmode.json#difficulty` &nbsp;·&nbsp; declared in `schema/difficulty.schema.json`

CKF Hard Mode - custom-difficulty slider range.

One key, and it is the whole section - in 3.0 it is the "difficulty" section of ckf.hardmode.json rather than the [Difficulty] section of the cfg. The 20 knobs that used to live here - MonsterHitPointScalar, PowerLevelScalar, MissionEconomy and the rest - were removed in 2.11.0. They were a second place to set values the game already exposes on its own custom-difficulty sliders, under its own names, and they had already produced a bug: two of them shipped non-NaN, so a fresh install silently doubled enemy HP.

This section's whole job is now to widen the game's own Min/Max bounds so those sliders reach further. Set difficulty in the game's window.

GameDifficultyModel's bound properties are STATIC, which took two failed runs to establish: Run28 dumped a materialized row and found 66 instance properties with not one bound among them. So widening is a one-shot on the type at load, not per row.

[PowerLevel] is unaffected by this section. It reads the model properties the sliders write, so it picks up whatever was set in-game.

### What the config GUI shows for this section

The GUI renders `uiDoc` where a subsystem has one and falls back to `doc` where it does not.

This does not set difficulty. It widens how far the game's own custom difficulty sliders can be pushed. You then set the difficulty itself in the game's own window. A ceiling is multiplied outward. A floor above zero is pulled closer to zero. A floor already below zero is pushed further down. A limit of exactly zero is left where it is.

## Elapse

**Mission Elapse Penalty** &nbsp;·&nbsp; `ckf.hardmode.json#elapse` &nbsp;·&nbsp; declared in `schema/elapse.schema.json`

CKF Hard Mode - mission elapse penalty.

When a mission's window closes unplayed the crew pays: credits off the balance, and Stress onto mercs linked to that contact. A mission with no contact - ContactId 0 - is skipped and costs nothing (Elapse.cs:742-747).

THIS SUBSYSTEM WRITES TO YOUR SAVE, through two channels, both proven against a live save by CKF Data Dump's WriteProbe before this subsystem was written (Elapse.cs:9-11):

```text
  credits  SaveManager.SpendCredits. The charge is capped to the live
           balance before it is asked for, so a 400 fine against a balance
           of 300 takes 300 and the balance never goes below zero
           (Elapse.cs:806-810).
  stress   GameCharacterModel.NegativeTraitValue, which is the Stress bar.
           The column named StressScore is the Discontent bar, not this one
           (Elapse.cs:22-23). The write goes to the engine's cached
           PlayerModel - what the roster panel reads - and to the database
           row (Elapse.cs:24-32). What the engine then does with a merc at a
           high Stress value is the engine's; this only feeds the number.
```

The penalty lands one turn after the window closes. The game stamps the expiry row with the turn that was ENDING and the hook reads GameTurn after it has advanced (Elapse.cs:35-38).

There is no stored progress and no high-water mark, so reloading to before an expiry and advancing again re-applies the penalty, and the same mercs take the Stress every time (Elapse.cs:58-62).

Every write this subsystem makes happens live. AGENTS.md section 6 records the standing instruction to test that way.

THE SHIPPED AMOUNTS ARE PLACEHOLDERS. ckf.hardmode.elapse.json:38-39 states that none of them has been played, and that they exist so the file parses and the first live sessions produce log lines to read. ## Fatigue

**Mission Fatigue** &nbsp;·&nbsp; `ckf.hardmode.json#fatigue` &nbsp;·&nbsp; declared in `schema/fatigue.schema.json`

CKF Hard Mode - mission fatigue.

A merc who completes a mission may come home Running Empty; a merc who deploys while already Running Empty is forced Off-Duty at mission end and the engine keeps them off the roster until it expires.

THIS SUBSYSTEM WRITES TO YOUR SAVE. It inserts GameCharacterTrait rows, which the game's own SaveManager.ProcessTraits expires on schedule. No new table, no new column, no side file and no tick of its own, so uninstalling the mod leaves at most a few live traits, which lapse by themselves (Fatigue.cs:89-91).

A LOST mission costs nothing. The game writes no score row of any kind on defeat, so the hook never fires there (Fatigue.cs:11-16).

Both stages are gated twice: [Fatigue] Enabled in ckf.hardmode.cfg before this file is opened (Fatigue.cs:343), and "enabled" below after it is loaded (Fatigue.cs:353).

Fatigue.cs still PARSES all eight keys and ignores them, so a config written before the removal keeps loading rather than being refused for keys that map to no member; a file carrying one gets a single log line at load naming what it found (Fatigue.cs:580-588, 664-693). Deleting them changes nothing.

The one behaviour that changed with them: a mission whose PowerLevel cannot be read used to fall back to the flat values. It now takes the LOWEST ANCHOR of each curve, which is what makes a one-anchor PL 1 curve behave exactly like the flat value it replaces (Fatigue.cs:1906-1922). The once-only warning about an unreadable PowerLevel is still there and says so.

## MissionRewards

**Per-Mission-Type Reward Overrides** &nbsp;·&nbsp; `ckf.hardmode.json#missions` &nbsp;·&nbsp; declared in `schema/missionrewards.schema.json`

CKF Hard Mode - per-mission-type reward overrides.

One entry per MissionTypeId. Blank slots do nothing. Slots use the adjustment syntax MissionRewards.cs:392-414 parses:

```text
   ""     leave the game's value alone
   "=40"  set it to 40
   "+25"  add 25 to whatever the mission shipped with
   "-25"  subtract 25
   "x1.5" multiply it   ("*1.5" is the same thing)
```

Anything else is logged as unparseable and ignored.

BonusPayment and BonusExperience are PERCENTAGES applied to the base reward curve, not credit amounts. PowerLevelBonus shifts the mission level. Those three are edited on the MissionRequestModel before the game does its own arithmetic, so they take effect when a mission is generated.

ObjectivePayment scales the mission's OWN cash terms - the per-file and per-target payments that carry no goal, no turn limit and no alarm ceiling, measured at 30% of the full job payment each (MissionRewards.cs:220-231, 272-276). SecondaryPayment scales CONDITIONAL cash rewards, the generated bonuses like 'finishing in 14 turns'. Both are the same RewardTypeId, which is why they get separate levers: without the split you could not raise what a Kill3 pays per target without inflating every generated turn-limit bonus attached to it. A row's 'Lever' field in the reference data says which of the two reaches it (scripts/refresh_mission_roster.py:270).

NEITHER SLOT REACHES A NON-CASH SECONDARY OBJECTIVE. Both act only on reward rows whose RewardTypeId is 7 or 13, the two cash types; a Blueprint, File, Influence or NBSCubes row is left alone, because scaling RewardQuantity there would multiply the number of blueprints (MissionRewards.cs:191-208). The top-level 'secondaryObjectives' block lists exactly those non-cash goals and nothing in the plugin reads it.

There is no pattern-bucket layer. The PureCombatTypes / SoloHackTypes lists and their bonus knobs were removed in 2.11.0; an exact MissionTypeId entry is the only way to reach a mission type.

The five slot columns - BonusPayment, BonusExperience, PowerLevelBonus, ObjectivePayment and SecondaryPayment - carry "format": "adjust", the adjustment grammar Adjust.Parse reads (MissionRewards.cs:392-415) and LoadOverrides applies to exactly those five and to no other column (MissionRewards.cs:325-329). 'type' and 'note' are plain strings.

The reward stack is two layers with no overlap: the "rewardcurve" section sets the base per power level, this section adjusts one mission type.

REGENERATING THE ROSTER. scripts/refresh_mission_roster.py rewrites this file after a play session. A 'shipped' value of null means that mission type has not been generated in a captured session yet, and a refresh fills it in. As the script stands it preserves your override slots, your // comment lines above an entry, and any JSON key it does not itself generate, and it refuses to write at all rather than lose a comment (refresh_mission_roster.py:154- 191, 464-467). The GUI's save path ends both of those guarantees: a hand-added comment or an unrecognised key is dropped.

REFERENCE KEYS THIS SCHEMA DOES NOT OWN. 'shipped', 'roomFlags', 'objectivePayments' and the top-level 'secondaryObjectives' block are annotations. The plugin deserialises none of them (MissionRewards.cs:261-263; nothing else in the source or scripts/ names the other three), so editing one changes no reward. They are not schema fields, no generator writes them, and the GUI must not offer them for editing. 'shipped' is already inconsistent with itself - the same column appears as ExpMod in 9 entries and ExperienceMod in 16 - and the dump plugin's CSV is canonical: regenerate these from it or drop them. A startup check. It reads a list of rows by id and compares their columns against values written down in advance, reporting pass or fail for each one. It is how you confirm a retune landed without running a full data sweep.

To use it, turn it on for one launch after a retune, read the block it prints, then turn it back off.

The expectations are a plain table - table, id, column, expected value, note - one row per check, edited in a spreadsheet. Leave the expected value blank and it reports what it found without judging it, which is a quick way to read a column you are unsure about.

It is only as good as the values you wrote down. An expectations file that has not been refreshed since your last retune reports failures that are only the file being out of date.

## Progression

**Team Power Level Award** &nbsp;·&nbsp; `ckf.hardmode.json#teampl` &nbsp;·&nbsp; declared in `schema/teampl.schema.json`

> **RETROACTIVE CONTROLS IN THIS SUBSYSTEM.** `enabled` and `override` re-price existing save data. Changing one does not only affect what happens next; it rewrites what already happened, and the substituted figure persists into the save.

CKF Hard Mode - Team Power Level award.

Team PL is a SUM over GameMissionScoreModel joined to MissionPowerLevelModel on (ActionClass, MissionPowerLevel). 'table' below is the game's own values, REFERENCE ONLY - the mod reconciles against it before it substitutes anything, and editing it changes no award. 'override' is what you edit.

It is a sum, not a counter, and that was verified exactly rather than approximately: the reference save's 127 mission rows sum to 7.7075 and its first 126 to 7.6925, which are the two numbers the trace printed either side of the insert that finished a PL 7 solo hack (Progression.cs:12-20).

The row itself carries no number. GameMissionScoreModel has six columns and no fraction among them - Id, MissionTypeId, MissionPowerLevel, ActionClass, GameTurn, MissionSuccessful - so the award is entirely a function of the two join keys (Progression.cs:26-32).

ACTIONCLASS - settled by the save, not inferred. Every one of the reference save's 127 completed missions was classed by the game itself (Progression.cs:70-81):

```text
  0  LEGWORK only, always PL 0, always worth nothing
  1  story missions and Power Play missions
  2  Treaty contracts - the standard proc-gen board
  3  solo hacks - every HackCPU / HackFile / HackLoot, whatever generated it
```

Class 3 wins over its source: M_PGenPower_Icarus_M1_HackCPU is class 3, not 1, and M_PGenTreaty_HackCPU is class 3, not 2.

Class 0 is worth nothing because the game's table has no class-0 band, not because the sum skips those rows: a row whose (ActionClass, MissionPowerLevel) has no cell contributes zero, and the arithmetic reconciles only if the 34 LEGWORK rows at (0, 0) are worth zero (Progression.cs:22-24, 142-144).

The victory screen reads a different path at a different time. The label rules that make it agree are generated into ckf.hardmode.d/ from 'override' - see the mirror invariant. Do not hand-write MissionPowerLevelModel rules in rules.json.

### What the config GUI shows for this section

The `uiDoc` array: the same subsystem written for someone playing the game rather than maintaining the mod. The GUI renders `uiDoc` where a subsystem has one and falls back to `doc` where it does not.

Your Team Power Level is a running total over every mission the crew has finished. Each completed mission is worth a fraction, looked up by what class of mission it was and what level it was at, and the total is the sum of all of them. This page replaces that table.

The new PL gains apply to missions you have already finished, which means you may see your PL spike up or down when you first load in.

The reference table is the game's own list for comparison.

The four mission classes are 0 for legwork, which grants nothing; 1 for story and Power Play missions; 2 for typical proc-gen missions; and 3 for solo hacks.

To tell it is working, look for the reconcile line in the log: before substituting anything the mod adds up the game's own values over the same missions and checks that its total matches. If that line is not there, it could not reproduce the game's total and has deliberately left your Team Power Level exactly as the game computed it.
