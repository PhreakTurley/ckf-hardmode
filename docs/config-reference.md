## Retroactive controls — read before changing these

A retroactive control re-prices existing save data. It is not a setting that takes effect from now on; it rewrites what has already happened, and the result persists into the save, so putting the control back does not put the save back.

| Subsystem | Field | What it re-prices |
|---|---|---|
| Progression | **`override`** | Per-cell replacement for the award. A cell absent here keeps its 'table' value, and a cell present here replaces it outright - the value is used verbatim, with no snapping to a game cell and no clamp of any kind in the code (Progression.cs:150-152, 340-342). A cell with no 'table' value works too: it simply contributes its own figure to the sum, and gen_teampl_labels.py emits its label rule marked '(no stock cell)'. THE RANGES BELOW ARE GUARD RAILS FOR THE EDITOR, NOT ENGINE LIMITS. ActionClass runs 0-3 because that is what the save files rows under; the game's table has no class-0 band, so a class-0 override has no stock value behind it and re-prices every LEGWORK row from zero. PowerLevelFraction is allowed to go negative because the game's own table does. A worked example: an override cell of ActionClass 2, MissionPowerLevel 7, PowerLevelFraction 0.015 makes Treaty contracts at PL 7 pay a solo hack's rate, 0.03 down to 0.015, and setting the same cell to 0 stops that class and level advancing the team at all. |

1 retroactive control(s). Every other control in this document takes effect from the next relevant event onwards.

## How to read the field tables

| Column | Meaning |
|---|---|
| `Path` | For `in: cfg`, `Section.Key`. For `in: json`, a dotted path from the sidecar root. Both are the literal address a generator writes to; neither is derived from the other. |
| `Default` | The value the schema declares. |
| `Absent` | What leaving the key out means, stated only where that differs from the default. Where this column has an entry, omitting the key and writing the default are two different things. |
| `Range` | Inclusive `[min, max]`. `check_schema.py` reports a value outside it as RANGE. |
| `Gated by` | A third enable level: a boolean elsewhere in the same file that must be true for this field to mean anything. |
| `Flags` | `RETROACTIVE` re-prices existing save data. `optional` means leaving the key out of the file is legal, so `check_schema.py` skips its `MISSING` check — it does **not** say what the omission means, which is the `Absent` column's job, and a field may carry one, both or neither. `one line` means a cfg list split across lines silently keeps only its first entry. `keyed by` means the block is a JSON object whose keys are that column, not an array. |

Table and matrix fields get a `Columns of ...` section of their own below. A column there may carry a `Format`, naming the grammar its cell text must parse under; that is a property of a value that is present, and is unrelated to `Absent` and `optional`.

## ConsumablesChems

**Chem Consumables** &nbsp;·&nbsp; `.cfg` section `[ConsumablesChems]` &nbsp;·&nbsp; declared in `schema/consumableschems.schema.json`

Slice toggle. Off: Slices.VerdictForOverlay skips every file below before it is opened, so none of its rows reach RulePlan. These files are loaded by the row-edit engine, so they also have no effect while [Slices] ModelRules is off (ModelRules.Init returns before Overlays.Load).

Files this toggle gates:

```text

```

ItemClass 4.

ItemModel's consumables are split into six sheets by ItemClass: 1 medical, 2 grenades, 3 devices, 4 chems, 6 sploitkits, 7 matrix. There is no ItemClass 5.

Lever sheet, not a direct overlay: the first column is ItemName, not a row id. Consumables.cs owns the whole parse and expands each row at load into writes on up to three tables: ItemModel keyed on ItemTypeId, TalentModel keyed on the row's TalentId, and the payload table keyed on the row's EffectId / MatrixEffectId. Lever cells take blank, =N, +N, -N or xN.

A blank identity cell means the row reaches no row of that table. Unlike Cyberweapons.cs and Implants.cs, Consumables.cs does not treat that as a malformed row; a payload cell on such a row is refused and named. A non-blank, non-integer id refuses the whole row.

In the game data all 18 chems carry an EffectModel payload [measured]. This sheet has the widest payload of the six: the union of the EffectModel columns those effects use, blank where unused.

Winternight Black applies StressRes -15 and nothing else. That is the game's own behaviour, not a mod change.

## Fatigue

**Mission Fatigue** &nbsp;·&nbsp; `.cfg` section `[Fatigue]` &nbsp;·&nbsp; declared in `schema/fatigue.schema.json`

CKF Hard Mode - mission fatigue.

A THREE-TIER TRACK. Every merc who completes a mission rolls once. A merc who fails the roll moves up one tier from the highest tier they already carry: nothing to tier 1, tier 1 to tier 2, tier 2 to tier 3. A merc already carrying tier 3 is not rolled, because there is nowhere above it. The trait granted at each tier is tier1.traitId, tier2.traitId and tier3.traitId (Fatigue.Resolve, Fatigue.Apply).

ONE ROLL FOR EVERY TIER. Moving up is not automatic - the same roll against the same chancePercent, with the same Wound Resist subtracted from it, decides a first grant and a move to tier 2 or tier 3 alike (Fatigue.ThresholdFor). There is one chance curve and one duration curve, and both apply at every tier.

TRAITS STACK. Moving up a tier does not remove the tier below it. All three shipped fatigue traits are TraitClass 6 in their own TraitGroup, so one merc can carry several at once and their penalties apply together. Each row expires on its own schedule, counted from the mission that granted it, so the lower tiers lapse first (Fatigue.Apply).

ONE POOL, ONE CLAMP. Everybody eligible to roll is in one pool, whatever tier they are on, and minAffected and maxAffected bound the TOTAL number of grants the mission makes. A floor can therefore force a move up a tier, and a ceiling can spare one; both reach for the mercs whose roll landed nearest their own threshold (Fatigue.Clamp).

THIS SUBSYSTEM WRITES TO YOUR SAVE. It inserts GameCharacterTrait rows, which the game's own SaveManager.ProcessTraits expires on schedule. No new table, no new column, no side file and no tick of its own, so uninstalling the mod leaves at most a few live traits, which lapse by themselves (Fatigue.Apply).

A LOST mission costs nothing. The game writes no score row of any kind on defeat, so the hook never fires there (Fatigue.AfterInsertGameScore).

SOLO MISSIONS ARE EXEMPT. A mission whose roster is one character runs none of this: no roll, nothing written (Fatigue.Resolve).

THE 4.0 LAYOUT IS RETIRED. runningEmpty and offDuty were two blocks with four byPowerLevel curves between them, and escalation to Off-Duty was unconditional. Both blocks still PARSE so that a 4.0 file loads instead of being refused for keys that map to no member, and a file carrying one gets a log line naming it, but nothing reads them. Their curves do not stand behind the two below (Fatigue.LegacyKeys).

A mission whose PowerLevel cannot be read takes the LOWEST ANCHOR of each curve, which makes a one-anchor PL 1 curve behave like a flat value. A once-only warning says so.

Missions tire the crew. Every merc who finishes one rolls once, and a merc who fails moves up one step: first to the tier 1 trait, then tier 2, then tier 3. ## MissionRewards

**Per-Mission-Type Reward Overrides** &nbsp;·&nbsp; `.cfg` section `[MissionRewards]` &nbsp;·&nbsp; declared in `schema/missionrewards.schema.json`

CKF Hard Mode - per-mission-type reward overrides.

One entry per MissionTypeId. Blank slots do nothing. Slots use the adjustment syntax MissionRewards.cs:392-414 parses:

```text
   ""     leave the game's value alone
   "=40"  set it to 40
   "+25"  add 25 to whatever the mission shipped with
   "-25"  subtract 25
   "x1.5" multiply it   ("*1.5" is the same thing)
```

Anything else is logged as unparseable and ignored.

BonusPayment and BonusExperience are PERCENTAGES applied to the base reward curve, not credit amounts. PowerLevelBonus shifts the mission level. Those three are edited on the MissionRequestModel before the game does its own arithmetic, so they take effect when a mission is generated.

ObjectivePayment scales the mission's OWN cash terms - the per-file and per-target payments that carry no goal, no turn limit and no alarm ceiling, measured at 30% of the full job payment each (MissionRewards.cs:220-231, 272-276). SecondaryPayment scales CONDITIONAL cash rewards, the generated bonuses like 'finishing in 14 turns'. Both are the same RewardTypeId, which is why they get separate levers: without the split you could not raise what a Kill3 pays per target without inflating every generated turn-limit bonus attached to it. A row's 'Lever' field in the reference data says which of the two reaches it (scripts/refresh_mission_roster.py:270).

NEITHER SLOT REACHES A NON-CASH SECONDARY OBJECTIVE. Both act only on reward rows whose RewardTypeId is 7 or 13, the two cash types; a Blueprint, File, Influence or NBSCubes row is left alone, because scaling RewardQuantity there would multiply the number of blueprints (MissionRewards.cs:191-208). The top-level 'secondaryObjectives' block lists exactly those non-cash goals and nothing in the plugin reads it.

There is no pattern layer: an exact MissionTypeId entry is the only way to reach a mission type.

The five slot columns - BonusPayment, BonusExperience, PowerLevelBonus, ObjectivePayment and SecondaryPayment - carry "format": "adjust", the adjustment grammar Adjust.Parse reads (MissionRewards.cs:392-415) and LoadOverrides applies to exactly those five and to no other column (MissionRewards.cs:325-329). 'type' and 'note' are plain strings.

The reward stack is two layers with no overlap: the "rewardcurve" section sets the base per power level, this section adjusts one mission type.

REGENERATING THE ROSTER. scripts/refresh_mission_roster.py regenerates the roster from CKF Data Dump output. A 'shipped' value of null means that mission type has not been generated in a captured session yet, and a refresh fills it in. The script preserves override slots, // comment lines above an entry and any JSON key it does not itself generate, and refuses to write rather than lose a comment. The GUI's save path does not keep those: a hand-added comment or an unrecognised key is dropped.

REFERENCE KEYS THIS SCHEMA DOES NOT OWN. 'shipped', 'roomFlags', 'objectivePayments' and the top-level 'secondaryObjectives' block are annotations. The plugin deserialises none of them (MissionRewards.cs:261-263; nothing else in the source or scripts/ names the other three), so editing one changes no reward. They are not schema fields, no generator writes them, and the GUI must not offer them for editing. The Data Dump's CSV is canonical for the game's values; read these annotations as notes.

## SpawnWeights

**Enemy Spawn Weights** &nbsp;·&nbsp; `.cfg` section `[SpawnWeights]` &nbsp;·&nbsp; declared in `schema/spawnweights.schema.json`

```text
  MonsterGroupMemberModel.spawn-jupiter.csv
  MonsterGroupMemberModel.spawn-kemco.csv
```

WHAT IT IS FOR. One file per faction. A MonsterGroupMemberModel row ties one enemy type to one spawn group and carries the weight that group rolls it with, so editing a row's weight changes how often that enemy type is rolled for a slot in that faction's opening roster at the power level the row covers.

THE WEIGHTS ARE RELATIVE, NOT ABSOLUTE. A roll is made among the rows eligible for the slot, so a weight only means anything next to the other weights in the same faction. Doubling every weight in one file changes nothing; doubling one of them changes that type's share.

THE BASELINE SCALE IS x100. The shipped numbers are written a hundred times larger than the ratio they express, so a typical weight reads 200, 400 or 1000 rather than 2, 4 or 10. The headroom is deliberate: it is what lets a weight be moved a little without rounding to nothing.

THERE IS NO FILE FOR A POOL NO GENERATED MISSION BUILDS. A faction whose FactionModel.ProcGenSelect is 0 is never picked for a generated mission, and a shared pool whose every user is such a faction is therefore never rolled. The Corp shared pool (MonsterGroupId 500) is the one case: its only user is Demo Corp. It carries no file, and the writer refuses rather than emitting one for any pool that becomes unreachable in a later dump.

WHICH ROWS ARE IN A FILE. Each file carries its faction's weakest enemy types, meaning the ones already eligible at power level 2 or below. The stronger types the faction fields later are not in these files.

ONE ROW CARRIES ONE WEIGHT, so a weight that varies with power level is written as several rows, each covering a single level. A row that covers one power level is therefore the mechanism for making a weight level-dependent, not a special case.

THE LOWEST-ENTERING TYPE TAPERS ONCE THE ROSTER IS FULL. Every pool finishes unlocking types at some power level, and above that level no new archetype enters and the band gates on a shipped row cannot be edited to change that. So the type that enters lowest is thinned instead: its TOTAL weight falls linearly from its x100 baseline at that last-unlock level to 1 at power level 20. Below the last-unlock level nothing changes, and every other type keeps its x100 baseline and absorbs the share the lowest type gives up.

AT POWER LEVEL 20 THE LOWEST TYPE HAS NO PER-LEVEL ROW. A per-level row carries the total minus what that type's own shipped rows already contribute, and at the end of the taper those are equal. A missing row at the top of one ladder is the mechanism reaching its floor, not a gap.

Each file is a direct overlay: the part of the filename before the first dot names the game table, and the "spawn-<faction>" part is the file's tag. There is no expander: the first column is MonsterGroupMemberId, the table's own id column, so overlay_kind_derived grades every one of these files `direct` and the grid's first column grades `identity`.

## Progression

**Team Power Level Award** &nbsp;·&nbsp; `.cfg` section `[Progression]` &nbsp;·&nbsp; declared in `schema/teampl.schema.json`

> **RETROACTIVE CONTROL IN THIS SUBSYSTEM.** `override` re-prices existing save data. Changing one does not only affect what happens next; it rewrites what already happened, and the substituted figure persists into the save.

CKF Hard Mode - Team Power Level award.

Team PL is a SUM over GameMissionScoreModel joined to MissionPowerLevelModel on (ActionClass, MissionPowerLevel). 'table' below is the reference copy of the game's values: the mod reconciles against it before it substitutes anything, and editing it changes no award. 'override' is what you edit.

It is a sum, not a counter, and that was verified exactly rather than approximately: the reference save's 127 mission rows sum to 7.7075 and its first 126 to 7.6925, which are the two numbers the trace printed either side of the insert that finished a PL 7 solo hack (Progression.cs:12-20).

The row itself carries no number. GameMissionScoreModel has six columns and no fraction among them - Id, MissionTypeId, MissionPowerLevel, ActionClass, GameTurn, MissionSuccessful - so the award is entirely a function of the two join keys (Progression.cs:26-32).

ACTIONCLASS - settled by the save, not inferred. Every one of the reference save's 127 completed missions was classed by the game itself (Progression.cs:70-81):

```text
  0  LEGWORK only, always PL 0, always worth nothing
  1  story missions and Power Play missions
  2  Treaty contracts - the standard proc-gen board
  3  solo hacks - every HackCPU / HackFile / HackLoot, whatever generated it
```

Class 3 wins over its source: M_PGenPower_Icarus_M1_HackCPU is class 3, not 1, and M_PGenTreaty_HackCPU is class 3, not 2.

Class 0 is worth nothing because the game's table has no class-0 band, not because the sum skips those rows: a row whose (ActionClass, MissionPowerLevel) has no cell contributes zero, and the arithmetic reconciles only if the 34 LEGWORK rows at (0, 0) are worth zero (Progression.cs:22-24, 142-144).

The victory screen reads a different path at a different time. The label rules that make it agree are generated into ckf.hardmode.d/ from 'override' - see the mirror invariant. Do not hand-write MissionPowerLevelModel rules in any overlay.

### What the config GUI shows for this section

The `uiDoc` array: the same subsystem written for someone playing the game rather than maintaining the mod. It carries no citations, run numbers or evidence tags by design — the prose above is the record, and this is the reader-facing summary of it. The GUI renders `uiDoc` where a subsystem has one and falls back to `doc` where it does not.

Your Team Power Level is a running total over every mission the crew has finished. Each completed mission is worth a fraction, looked up by what class of mission it was and what level it was at, and the total is the sum of all of them. This page replaces that table.

The new PL gains apply to missions you have already finished, which means you may see your PL spike up or down when you first load in.

The reference table is a copy of the game's own values, for comparison.

The four mission classes are 0 for legwork, which grants nothing; 1 for story and Power Play missions; 2 for typical proc-gen missions; and 3 for solo hacks.

To tell it is working, look for the reconcile line in the log: before substituting anything the mod adds up the game's own values over the same missions and checks that its total matches. If that line is not there, it could not reproduce the game's total and has deliberately left your Team Power Level exactly as the game computed it.
