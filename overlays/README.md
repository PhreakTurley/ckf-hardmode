# Enemy scaling overlay set — PL 1-20

Every gear family an enemy walks, laid out as 20 tiers — one per power level —
in CSV files the Hard Mode loader reads. **The set itself is not in this
folder.** Its one copy is the game's `BepInEx\config\`: `ckf.hardmode.rules.json`
and `ckf.hardmode.d\` (`ArmorModel.csv`, `WeaponModel.csv`,
`MonsterTypeModel.csv`). Generated by
`scripts/make_enemy_overlays.py` from `BepInEx/ckf-dump/` and
`ckf.hardmode.rules.json`. Format: [`../docs/overlays.md`](../docs/overlays.md).
What the cells mean: [`../docs/tuning-enemies.md`](../docs/tuning-enemies.md).

## Installing

Commands, validation and in-game testing are in
[`../docs/workflow.md`](../docs/workflow.md). Tuning is an edit to the live
`ckf.hardmode.d\` in place; nothing here is copied into the game. Installing
only comes up after a regenerate, and then two things apply to the generator's
output:

- **Both, or neither.** Its rewritten `rules.json` no longer inserts the enemy
  gear tiers the pointers aim at, so installing it without its CSVs is a black
  screen.
- **Back up the live `rules.json` first**; installing the output overwrites
  it. The regenerate step below reads `_reference/rules-original.json`, the
  file this set was generated from, not the live one.

## Where all 20 tiers are

**Every gear family an enemy walks is 20 tiers, one per power level.** 29 blocks
— 9 armour, 20 weapon — covering all 120 PowerGroups that exist at more than one
power level. The remaining 25 are single-power-level enemies (story guards,
target dummies, VIPs); a ladder means nothing for them and their shipped
pointers are untouched. `_reference/gear-blocks.md` names them all.

**Start at `_reference/gear-tiers.csv`.** 580 rows, 29 blocks x 20 power levels,
every one accounted for: 208 are rows the game ships and 372 are clone lines in
the set. `ProvidedBy` names the file. Nothing comes from `rules.json` any
more, and the generator refuses to write unless all 580 resolve.

To point an enemy at its tier you do not have to look anything up: **the
pointers are already correct in `MonsterTypeModel.csv`**. Go to `gear-tiers.csv`
for the reverse — "which file holds the numbers for sniper armour PL 17" — and
to `powergroups.csv` when you have an enemy and want its blocks.

**A ladder file's line count is not its block's size.** `ArmorModel.sniper.csv`
has 14 lines for a 20-tier block because 6 of the tiers are rows the game
ships. Read the `tiers (shipped/new)` column in `gear-blocks.md`.

## Overlay syntax

- **A cell is a plain number.** The operator lives in the header: `Col` set,
  `Col*` multiply, `Col+` add, `Col>` clampMin, `Col<` clampMax.
- **An empty cell means "leave alone."** Clearing a cell backs out a change.
- Clone lines state **every** column their block's edit file states, so a tier
  never inherits a number from the row it was cloned from.

What each column does, and which are traps, is
[`../docs/tuning-enemies.md`](../docs/tuning-enemies.md). The full format spec is
[`../docs/overlays.md`](../docs/overlays.md).

## Two shipped breaks this set repairs

- `Hover Tank` PL 1 pointed at `ArmorTypeId` 22510, which is not in
  `ArmorModel`. PL 1-10 now walk 22511-22520, one row per level.
- `J4 FireCOM` and `J3 Extinguisher` PL 11-20 pointed at `WeaponTypeId`
  23140-23149, none of which existed. `WeaponModel.jfam.csv` creates them —
  no pointer change was needed.

## The 21 warnings

```
WARN  edits a clone source
  ArmorModel.guard-standard-base.csv:12   (ArmorModel 22009)
  ... and 20 more, one per block
```

Every block's PL 10 row is both an edited row and the source its PL 11-20 tiers
clone from. **They are warnings, never load failures.**

The mechanism they warn about is closed: every clone line states every column the
matching `-base` file states, so a clone inherits no number from its source. The
headers are identical, which is checkable:

```
python -c "print(open('ArmorModel.guard-standard.csv').readline());print(open('ArmorModel.guard-standard-base.csv').readline())"
```

What a clone still takes from its source is the columns no CSV names —
`ArmorClass`, the name, and on weapons `WeaponClass`, `ModeType`, `AngleFire`,
`SpecialRule`, `PrecisionRule`, VFX. Nothing edits those, and sourcing from
outside the block would be worse: the nearest lookalike from another family
differs on exactly them.

**If you edit a `-base` row, re-record any SelfCheck expectation for the tiers
cloned from it.**

## What stayed in rules.json, and the convention

**Player-directed gear rules stayed** — the `RecoilRate2` full-auto sweep and
the sixteen 25000-25015 optical lasers, which no enemy carries.

The split is **declared, not inferred**: a gear rule whose comment starts with
`PLAYER` stays in `rules.json` and this generator never restates its effect in a
CSV, so retuning it still takes effect. The rules it writes out already carry the
prefix — keep it, and add it to any new player gear rule. Which ids are
player-facing and which are enemy-facing is
[`_reference/player-vs-enemy-gear.md`](_reference/player-vs-enemy-gear.md); it
also holds the 16 `whereMin`/`whereMax` pairs the `PLAYER` rules now use.

**Enemy gear rules did not stay.** No `ArmorModel` rule remains, no enemy
`WeaponModel` rule remains, and neither do the `MonsterTypeModel` rules that
aimed gear pointers. `_reference/rules-removed.json` holds the originals.

## Regenerating

Regenerating is a reset: it discards every edit made since.

- **`--rules` must point at a `rules.json` that still contains the lifted
  enemy-gear rules.** Point it at the rewritten file and the baked values revert
  to shipped. `_reference/rules-original.json` is exactly that file, kept for
  this reason, so a regenerate from inside this folder always works.
- **A new `PLAYER`-prefixed rule you add to the live `rules.json` must be added
  to `_reference/rules-original.json` too**, or the next regenerate will not
  know to leave it alone.

```
python "D:\ckf-data-modding\scripts\make_enemy_overlays.py" --dump "C:\Program Files (x86)\Steam\steamapps\common\Cyber Knights Flashpoint\BepInEx\ckf-dump" --rules "<original rules.json>" --out "<empty folder>"
```

`--out` receives the whole set plus its own `README.md` and `_reference/`,
overwriting what is there, so give it an empty folder, not this one (this
command used to name `D:\ckf-data-modding\overlays`). The output is per family;
the live set is one file per table, which
`scripts/merge_overlays.py --write --src <out> --out <dir>` produces.

## State of the set

- **The values are not the shipped ones.** [measured] Retuned to PL 20 on
  2026-08-26.
  Every gear ladder rises across all 20 power levels, and `MonsterTypeModel`
  CritRate / InitBonus / FlankAllowance / ShotLimit / MaxTalentCount /
  MovePoints carry the retuned curves. `scripts/validate_rules.py` prints
  `0 error(s)`.
- **HitPoints is deliberately untouched.** The developers carried it to PL 20
  themselves. Exactly three cells moved, all repairs of breaks: Marcus PL 11,
  MG Turret PL 20, EG Turret PL 20.
- **Every number was refitted from `BepInEx/ckf-dump/`**, not from the previous
  contents of this folder. Earlier passes left placeholder values in
  `ArmorModel.guard-standard-base.csv` and `WeaponModel.guard-rifle-base.csv`;
  they were discarded. If you retune again, take the shipped dump as ground
  truth.
- **Enemy gear lives in the overlay CSVs, not in `rules.json`.** 122 enemy-gear
  rules were lifted out of that file and re-expressed as these CSVs. **Cloning
  is driven from the CSVs too:** the ladder files carry a `_clone` column, and the live
  `ckf.hardmode.rules.json` has zero clone rules. [measured]
- **Player-directed gear stays a rule** — 33 of them, prefixed `PLAYER` in their
  comment. Nothing in these CSVs restates what a `PLAYER` rule does.
- **The player/enemy weapon split is finished.** `blade5`, `sniper6`, `thrasher`
  and `shock` PL 1-10 were cloned out of the player rows they borrowed into
  `900160`-`900199` and every archetype repointed. **No full-ladder enemy points
  below `WeaponId` 20000 any more.** [measured]
