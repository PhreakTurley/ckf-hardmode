# CKF Hard Mode

Use this page to build the plugin DLL, find the source and config file for a
subsystem, and interpret startup logs. Every key, type and default is generated
from `schema/*.schema.json` into
[`../../docs/config-reference.md`](../../docs/config-reference.md); this page
does not duplicate that reference.

The plugin changes how the game plays. Reading the game (table dumps, member dumps, method traces) is done by CKF Data Dump (`mods/CKFDataDump/`, not published), a separate plugin with its own GUID and config. Neither plugin depends on the other.

The public plugin version is `4.1.1` (`Plugin.PluginVersion` and
`CKFHardMode.csproj`). The independent settings-layout stamp is `4.1.0`
(`Defaults.DocVersion` and each settings file's `_version`).

## Subsystems

`ckf.hardmode.cfg` has 46 keys: `[General] Enabled` and 45 `[Slices]` switches
(`Plugin.Binds.g.cs`, generated by `scripts/gen_binds.py`). Every file below
lives in `BepInEx/config/ckf.hardmode.d/` unless a path is given.

### Settings subsystems

Listed in the order `Plugin.Load` starts them. JSON settings files are read by `ConfigDoc.cs`; StunClub uses only its cfg switch.

| Switch | Source | File | What it does |
|---|---|---|---|
| `[General] Enabled` | `Plugin.cs`, `Slices.cs` | `ckf.hardmode.cfg` | Master switch. When it is `false`, nothing is patched and nothing is written to the save. |
| `ModelRules` | `ModelRules.cs`, `Overlays.cs`, `RulePlan.cs`, `RowClone.cs`, `Accessors.cs`, `Writability.cs` | `modelrules.json` | The rule engine. It applies every overlay and lever sheet in `ckf.hardmode.d/` and inserts cloned rows. When it is off, none of its overlays apply, whatever the content switches say. |
| `SelfCheck` | `SelfCheck.cs` | `selfcheck.json`, `BepInEx/config/ckf.hardmode.selfcheck.csv` | Checks named rows' columns against expected values. A diagnostic; defaults to `false`. |
| `PowerLevel` | `PowerLevelCap.cs` | `powerlevel.json` | Recomputes mission Power Level and clamps it to `[minCap, maxCap]` (and to `matrixMaxCap` on Matrix missions) instead of the game's ceiling of 10. |
| `Progression` | `Progression.cs` | `teampl.json`, `MissionPowerLevelModel.generated.json` | Replaces the Team Power Level each completed mission awards, per `(ActionClass, MissionPowerLevel)` cell. Changes are retroactive: every past mission is re-priced. The `.generated.json` file copies the values onto the victory-screen label. |
| `Fatigue` | `Fatigue.cs` | `fatigue.json` | A three-tier fatigue track (Checked Out, Running Empty, Off-Duty). One roll per merc per completed mission moves a failure up one tier, scaled by power level and reduced by Wound Resist. Writes to the save. |
| `Elapse` | `Elapse.cs` | `elapse.json` | When a mission's window closes unplayed, takes credits and adds Stress to mercs linked to that contact. Writes to the save. |
| `MissionRewards` | `MissionRewards.cs` | `missions.json` | Sets payment, XP and power-level bonus per `MissionTypeId` before the game does its own reward arithmetic. |
| `RewardCurve` | `RewardCurve.cs` | `rewardcurve.json` | Replaces the game's hardcoded baseline payment, XP and bonus step table, keyed on `PowerLevelUnscaled`. |
| `StunClub` | `StunClub.cs` | `ckf.hardmode.cfg` only | Optional attack-scoped club change. Implementation, rollback and live checks: [Stun Club](../../docs/stunclub.md). |
| `Difficulty` | `Plugin.cs` | `difficulty.json` | Widens the `Min`/`Max` bounds of the game's custom-difficulty sliders. It sets no values; the in-game sliders still do that. |

`Fatigue` and `Elapse` both default to on, and both write to the save. Fatigue inserts `GameCharacterTrait` rows and deletes none. Elapse calls `SaveManager.SpendCredits` and writes `NegativeTraitValue` through the cached `PlayerModel`. Back up your saves before the first real run: `%USERPROFILE%\AppData\LocalLow\TreseBrothersGames\CyberKnights\`.

### Content slices

These files are data for the rule engine, so they apply only while `ModelRules` is on. A lever sheet is a CSV whose rows are player concepts; the plugin expands each row into rules when the game loads. Direct overlays are covered in [`../../docs/overlays.md`](../../docs/overlays.md).

| Switch | Source | File(s) | What it does |
|---|---|---|---|
| `GearClasses` | `GearClasses.cs` | `gear-classes.csv` | Lever sheet with one row per player weapon class. Classes resolve against the post-overlay `WeaponTypeId` set in `MonsterTypeModel.csv`, not the shipped table; if that file is missing or unreadable, the sheet emits no rules and the log says why. |
| `CyberweaponsClaws`, `CyberweaponsLasers` | `Cyberweapons.cs` | `cyberweapons-claws.csv`, `cyberweapons-lasers.csv` | Lever sheets. Each row becomes a `WeaponModel` rule and a `TalentModel` rule. |
| `ImplantsGlobal` | `Implants.cs` (`ExpandGlobal`) | `implants-global.json` | Three multipliers applied to every `ImplantModel` row. |
| `ImplantsSlot01` … `ImplantsSlot11` | `Implants.cs` | `implants-slot01.csv` … `implants-slot11.csv` | Lever sheets, one per implant slot. Each row becomes an `ImplantModel` rule and an `EffectModel` rule. |
| `ConsumablesChems`, `ConsumablesDevices`, `ConsumablesGrenades`, `ConsumablesMatrix`, `ConsumablesMedical`, `ConsumablesSploitkits` | `Consumables.cs` | `consumables-<family>.csv` | Lever sheets. Each row can expand into rules on up to four tables: `ItemModel`, `TalentModel`, `EffectModel` and `MatrixEffectModel`. |
| `RuleModel` | `Overlays.cs` | `RuleModel.csv` | Direct overlay of the game's rule constants. |
| `SpawnWeights` | `Overlays.cs` | `MonsterGroupMemberModel.spawn-*.csv` (12 files) | Direct overlays for the faction spawn pools declared by `spawnweights.schema.json`. |
| `Talents<Class>` (11) | `Overlays.cs` | `EffectModel.<tag>.csv`, `JobNodeModel.<tag>.csv`, `TalentModel.<tag>.csv`, and `MatrixEffectModel.hkr.csv` for the Hacker | Direct overlays for one class's talent rebalance. Tags: `aex ck cs gs hkr sc sn sol vg wg wm`. |
| `LimitBreakTraits` | `Overlays.cs` | `EffectModel.limitbreak.csv` | Direct overlay of the `EffectModel` rows behind the shipped Stress Limit Break traits, which is what a limit-break trait does to the merc carrying it. Its own switch rather than `Fatigue`'s: that one decides who is granted a trait and when. |
| none | `Overlays.cs` | `ArmorModel.csv`, `WeaponModel.csv`, `MonsterTypeModel.csv` | Enemy gear overlays. No slice claims them, so they load unconditionally and the log names them as "claimed by no slice". |

The file-to-switch mapping is `Slices.OverlayOwner`. Five switch keys use older class names. Renaming a key would orphan the value a player has saved, so the keys and the talent schema filenames (the filename is the binding) keep the old names; each schema's `title` has the real one.

| Key | Class | Tag | JobId [measured] |
|---|---|---|---|
| `TalentsAEX` | Agent EX | aex | 5 |
| `TalentsCS` | Cybersword | cs | 3 |
| `TalentsSawbones` | Scourge | sc | 15 |
| `TalentsWarMachine` | Warmachine | wm | 2 |
| `TalentsWraith` | Wireghost | wg | 19 |

JobIds come from joining `JobNodeModel.<tag>.csv` → `JobNodeModel.JobId` → `JobModel.JobName`.

## Build the DLL from source

Players install the release zip; they do not need this source-build path. A
source build produces the DLL only and does not recreate or package the loose
configuration files.

### Install BepInEx 6 (IL2CPP)

BepInEx 6 is required, because BepInEx 5 has no IL2CPP support. The release zip bundles the pinned build (see [`../../vendor/README.md`](../../vendor/README.md)). For a manual install, extract `BepInEx-Unity.IL2CPP-win-x64` into the game root, which is the folder holding the game `.exe` (not `_Data`).

The first launch generates the Il2CppInterop assemblies and takes noticeably longer than later launches. After it finishes, these should exist:

```
<game>/BepInEx/LogOutput.log
<game>/BepInEx/interop/CoreRPG_v1.dll     RPG.Database.* lives here
<game>/BepInEx/plugins/
```

If `interop/CoreRPG_v1.dll` is missing, interop generation did not finish, so check `LogOutput.log`. After a game update, BepInEx regenerates the interop assemblies on the next launch. If the plugin then logs `Could not resolve …`, the game renamed something. Point CKF Data Dump's `[Diagnostics] DumpMembers` at the type to find the new name.

### Build

Requires the .NET SDK (6.0 or newer). The project targets `net6.0`.

```
cd mods\CKFHardMode
dotnet build -c Release -p:GameDir="C:\Path\To\Cyber Knights Flashpoint"
```

`GameDir` defaults to the standard Steam path (`CKFHardMode.csproj`). References resolve from `<GameDir>\BepInEx\core`. If `<GameDir>\BepInEx\plugins` exists, the build copies `CKFHardMode.dll` into it.

The DLL embeds no config. A tuning change therefore needs no `dotnet build`:
edit the live config and relaunch. Building the complete player zip is a
separate maintainer-only path; see
[`../../docs/workflow.md`](../../docs/workflow.md).

## Config loading

The config is read once at startup, and nothing re-reads it afterwards. Relaunch for any change to apply.

1. `Slices.Init` binds all 46 keys. It runs before the master-switch check, so BepInEx writes every line even when `Enabled = false`. If a key's bind throws, the key is reported at Error and treated as on.
2. If `[General] Enabled` is false, the plugin stops.
3. `Defaults.Install` checks the 17 paths in `Defaults.Expected`. It writes
   nothing and recreates no deleted file; it logs a count and names each
   missing file. The release supplies 16 paths from
   `make_release.py:CONFIG_FILES` and renders `ckf.hardmode.cfg` from
   `release/ckf.hardmode.cfg.in`.
4. `ConfigDoc.Init` reads the ten settings files (the nine subsystems plus `implants-global.json`). It reports unknown keys, duplicate keys and `_version` stamps that differ from `Defaults.DocVersion`. It fills in no missing keys: a key absent from an old file takes the subsystem's built-in default.
5. The both-layouts check (below) runs.
6. `ModelRules.Init` checks its switch and reads `modelrules.json`. It then runs `Overlays.Load`, which reads every `.csv`, `.tsv` and `.json` in `ckf.hardmode.d/` in ordinal filename order. Settings files are skipped by name (`ConfigDoc.OwnsFile`), and so is any file whose slice is off. A skipped file is never opened.
7. The remaining subsystems start in the order of the first table above.

The overlay directory is flat, and no config key points at it. The per-row file format is in [`../../docs/overlays.md`](../../docs/overlays.md), and rule semantics are in [`../../docs/rule-engine.md`](../../docs/rule-engine.md).

`ckf.hardmode.rules.json` is not part of the current slice layout. The plugin
still checks for it but never creates it. If it is present, `Plugin.Load` logs
`ModelRules: … IS ON DISK` at Error, and while `ModelRules` is on
`ModelRules.LoadRules` reads it before every overlay. Delete it.

A leftover `"enabled"` key in a settings file is not read. Its gate is the `[Slices]` key. The plugin logs a warning, or an Error if the old value was `false` and the slice is on this launch (`Slices.ReportRetiredGate`).

### Both layouts present: refusal

If `BepInEx/config/ckf.hardmode.json` (the pre-4.0 merged document) exists and any of the ten settings files exists too, the plugin refuses to run for that launch (`ConfigDoc.BothLayouts`). It logs:

```
ConfigDoc: BOTH CONFIG LAYOUTS ARE ON DISK. …
Plugin: stopping here. The game runs UNMODIFIED this launch. …
```

`Plugin.Load` then returns before the difficulty hook and `ModelRules.Init`. No
rule is compiled, nothing is patched, and no file is written or renamed. The
check runs after `Slices.Init`, so the `.cfg` still gets all 46 lines.
Extracting a zip never deletes files, so a player upgrading from 1.0.0 must
delete `ckf.hardmode.json` by hand. The root README and the zip's `README.txt`
say so. The refusal must not be softened: it stops the mod from silently
picking one of two copies of a player's tuning.

Converting an old config directory (`serve.py --migrate`) is a maintainer tool, not part of a player upgrade. See [`../../gui/README.md`](../../gui/README.md).

## Reading the log

Everything below is written to `BepInEx/LogOutput.log`. Each quoted fragment was checked against the source.

### Startup

| Line starts with | Source | What it tells you |
|---|---|---|
| `Disabled via config; nothing patched.` | `Plugin.Load` | `[General] Enabled` is false. Check for this line first when nothing happened at all. |
| `Slices: 46 key(s) declared in Plugin.Binds.g.cs, …` | `Slices.Init` | On/off/unreadable counts, and the name of every key that is off. |
| `[Slices] <Key> is false in ckf.hardmode.cfg — …` | `Slices.OffBecause` | One line per switched-off subsystem. |
| `Defaults: N of 17 config file(s) present.` | `Defaults.Install` | Error when any file is missing, followed by one `Defaults: missing <path>` line per file. |
| `ConfigDoc: _version stamps — …` | `ConfigDoc.ReportStamps` | Files stamped with a version other than `Defaults.DocVersion`. |
| `ConfigDoc: <dir> — N of 10 slice file(s) found` | `ConfigDoc.ReportSummary` | Missing, unusable and stray-key counts. |
| `ModelRules: no ckf.hardmode.rules.json in …` | `Plugin.Load` | Expected in the current slice layout. |
| `Overlays: N file(s) in the directory, …` | `Overlays.Load` | Settings files skipped, files read, lever sheets expanded, files skipped because their slice is off, files claimed by no slice, rows merged and inserts. |
| `Overlays: SKIPPED <file> [Slices] <Key> — …` | `Overlays.Load` | A file that was not opened because its slice is off. |
| `ModelRules: loaded N rule(s) across M model type(s)` | `ModelRules.Init` | The compiled rule plan, followed by one line per hooked table. |
| `ModelRules: no materializer for …` | `ModelRules.Init` | A rule names a table that does not exist, so it never fires. |

The per-table plan lines look like this:

```
  EffectModel: 133 rule(s) indexed on EffectId — …
  RuleModel: 2 rule(s), no index (every row tests all of them)
```

`no index` means every row is tested against every rule, which is fine for a few rules. Indexing is described in [`../../docs/rule-engine.md`](../../docs/rule-engine.md).

### Confirming a rule landed

Set `traceRules` in `modelrules.json` to N to log the first N rows each rule changes. The plugin logs a warning while this is on.

```
  trace #<index> <Table>[<id>] PL <n>: <Column> <before> -> <after>
```

A trace that reads `matched, nothing changed` means the rule matched a row but did not change it. This is what a read-only or recomputed column looks like.

Rows are read only when the game needs them, so a rule on high-PL archetypes traces nothing at the main menu. [`../../docs/workflow.md`](../../docs/workflow.md) describes how to force a read.

### When a rule looks applied and changes nothing

Some columns have a setter that discards the written value: the unsuffixed weapon stats (`Accuracy`, `BallisticDamage`, `ActionPoints`) alias the selected firing mode, and the talent `Adjusted*` columns are derived. Setting `probeWritableColumns: true` in `modelrules.json` works through one row per table: it writes a test value, reads it back, restores the original and records the result in `BepInEx/ckf-hardmode/writable_columns.csv`. The plugin also logs one `ModelRules: probed <Table> — …` line per table.

```
Table,Column,Type,Verdict,Detail
WeaponModel,Accuracy,Int64,ignored,"wrote 61, read back 60"
WeaponModel,WeaponName,String,read-only,
```

Verdicts are `writable`, `ignored`, `read-only` and `skipped`. The probe writes on the game's hot path, so turn it on for one launch only.

### Difficulty

```
Difficulty: GameDifficultyModel — <n> properties, <p> Min/Max pair(s), widened <w> by x<m>.
  PowerLevelScalar [0.75, 1.5] -> [0.25, 4.5]
```

A Harmony postfix on `GameDifficultyModel.ReconfigureDifficulty` and `ConfigureDefaults` widens the bounds after the game has configured difficulty. `sliderRangeMultiplier` scales each bound by its direction: a positive ceiling is multiplied, a negative floor is multiplied further down, a positive floor is divided toward zero, and a zero bound is left alone. Bounds are scaled from the values captured the first time the model is seen, so repeated reconfigures do not compound the widening. A multiplier of `1` leaves the stock ranges.

### Progression

`Progression: reconciled <sum> over <n> row(s).` means the plugin recomputed the game's own Team PL sum exactly, so the override can be applied. If the two sums disagree, the subsystem disables itself and logs why. How the award works is covered in [`../../docs/power-level.md`](../../docs/power-level.md#progression-team-pl-award-per-mission).

### Fatigue

`logGrants` logs one line per merc per mission, plus a summary. The head line ends `Tiers: 2007 -> 2009 -> 2014`, whatever the three `tier<N>.traitId` values are. Each merc line names the tier they were on, their roll against their threshold, the tier and trait they moved to, and the Wound Resist behind the threshold, including `safehouse` and `strength` contributions, for example `[<base> base - +N resist (strength +N, gear +N); read trait N, effect N, implant N (N with WoundRes, N via DataDb), job N]`.

- The summary counts grants per tier, then `clear` and `already at the top of the track`.
- `via DataDb`: the row came back without its joined effect, so the plugin looked the effect up. `UNRESOLVED`: that lookup failed and the row counted as 0.
- `safehouse module read INCOMPLETE` or `UNRESOLVED`: the built-module total could not be fully read, so the plugin uses the safehouse row's computed or summary value where available.
- `Fatigue: a save was loaded — …`: the load hook fired. If this line never appears after a load, report it; the replay guard still covers reloads.
- A warning naming `ReadGameCharacter`: that reader failed, so no merc is recognised as the Cyber Knight.
- `Solo missions are exempt`: missions with one merc roll nobody.
- `already on tier N, the top of the track. Not rolled.`: there is no tier above them, so nothing happens.
- `not resolved for want of a configured value`: the curve named no `chancePercent` or no `durationDays` at this power level, so those mercs were neither rolled nor granted. Counted apart from `clear` and from a failed write.
- `Fatigue: <path> still carries …`: the file still has the retired 4.0 `runningEmpty` or `offDuty` block. Both parse and neither is read, and their curves do not stand behind the current one — a file naming no top-level `byPowerLevel` is refused and the subsystem stays off for the launch.

Design and settings: [`../../docs/character-fatigue.md`](../../docs/character-fatigue.md).

### Elapse

On the first tick of a session:

```
Elapse: first tick of the process at turn <t>: <n> game-log row(s), <k> of them LogTypeId 202; board <b> mission(s), <c> with a contact, PowerLevelUnscaled <lo>-<hi>; highest log row id <id>. …
```

This line shows that the reader can see the game log. After a load the line says `first tick after a session reset`. A save with expired missions that reports `0 of them LogTypeId 202` points to a broken reader.

Credit spends are logged at warning level as `Elapse: WROTE credits: SpendCredits(…)`. A stress write must say `via cached PlayerModel`, because a write that reaches only the row does not move the in-game bar. Warnings to act on:

- `has no match in the previous board snapshot`
- `two live missions share the title`
- `came back null or unconvertible`
- `The write may not have taken.`
- `no cached PlayerModel for merc`

Design: [`../../docs/mission-elapse-penalty.md`](../../docs/mission-elapse-penalty.md).

## Notes

- Editing `DataDb` content models changes base data for every save. Editing `Game*` models writes into the current save.
- Harmony ids: `ckf.hardmode.models`, `.powerlevel`, `.progression`, `.fatigue`, `.elapse`, `.missionrewards`, `.rewardcurve`, plus `ckf.hardmode` for the difficulty hook (`Plugin.Load`).
- `MissionRewards` logs the first 40 generated missions (`MissionRewards.LogFirstMissions`); no key changes that.
- Merc bars are read from `SaveManager.playerCache[id].CharacterModel`, so a save-writing subsystem writes both the row and the cached model (`Elapse.cs` header).
- Traps: [`../../docs/gotchas.md`](../../docs/gotchas.md).
